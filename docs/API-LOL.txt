================================================================================
1. DECISIÓN: QUÉ API USAMOS Y POR QUÉ
================================================================================
Usamos la API oficial de Riot Games + Data Dragon. Nada más.

Motivos:
  - Es la ÚNICA fuente gratuita, legal y estable de datos por jugador
    (partidas, resultado, campeón, KDA, cola, duración).
  - No hay plan pago: todas las keys son gratis. El costo real es el rate limit.
  - Las alternativas (OP.GG, U.GG, DeepLoL, Mobalytics, LeagueOfGraphs,
    LoLalytics) NO tienen API pública documentada; su JSON interno es
    indocumentado, rota, está detrás de Cloudflare o prohibido por sus ToS.
  - Además, todas ellas están aguas abajo de la misma API de Riot, así que
    heredan el mismo tope de historial (ver sección 2). Scrapearlas no te da
    más datos: te da menos y con riesgo legal.
  - Data Dragon (oficial, sin key, sin rate limit) resuelve el join
    championId -> nombre/icono/tags y los nombres en español.

Descartados y por qué (resumen; detalle en research/03-alternatives.md):
  OP.GG            : sin API pública; ToS prohíbe scraping (su FAQ se contradice).
  U.GG             : robots.txt bloquea toda URL con query string; Cloudflare JS.
  DeepLoL          : api.deeplol.gg no existe (NXDOMAIN); sin docs.
  Mobalytics       : solo widgets para streamers.
  LeagueOfGraphs   : robots.txt con Disallow: /api/*.
  LoLalytics       : scrape frágil, anti-bot.
  RapidAPI (proxies): revendedores; el precio es por request y viola la política
                     de registro/reenvío de Riot.
  LoL Esports API  : solo partidas profesionales (útil para un futuro tab de esports).
  Leaguepedia Cargo: solo profesional + requiere bot password.

================================================================================
2. LÍMITE CRÍTICO: NO EXISTE "TODAS LAS PARTIDAS DE LA CUENTA"
================================================================================
Esto define el producto. Leerlo antes de diseñar la UI.

La API de Riot devuelve, como máximo, las últimas ~1000 partidas del jugador
(no es un parámetro: es un tope del backend).

  [SECONDARY] Esto NO figura en la documentación oficial: sale de un comentario
  de un dev de Riot en el tracker público (RiotGames/developer-relations,
  issue #957, 2024-07-15) y de la política de retención de 2019.
  Texto exacto del comentario:

  "Match data is retained for 2 years, match timelines for 1 year. A player's
   match list will only show up to the last 1000 matches played. Non-public
   games (customs, practice tool, etc.) count towards the 1000 match limit so
   it may never hold exactly 1000. Games exceeding the limit but not exceeding
   the retention period will only be accessible through the match list of
   another player that participated in the game, or directly by the match id."

Consecuencias para league-page:
  - "Campeón más jugado en el total de la cuenta" NO se puede cumplir al 100%.
    Se redefine como: "campeón más jugado en las últimas N partidas recuperables
    (máx. ~1.000, ventana de 2 años)".
  - En la UI SIEMPRE hay que mostrar la base del cálculo:
      "Campeón más jugado — 320 partidas analizadas (de las últimas 1.000,
       límite de la API de Riot), desde 12/03/2025 hasta 24/11/2026."
    Sin ese texto el número es engañoso y el usuario va a reportar "está mal".
  - Jugadores con mucho historial verán 950-1000; cuentas nuevas, 40. Los
    customs y remakes consumen cupo, así que rara vez son exactamente 1000.
  - Partidas fuera del tope pero dentro de los 2 años SÍ se pueden traer por ID
    directo (/matches/{matchId}), pero necesitás el ID desde el historial de
    OTRO participante. No es un camino viable para stats propias; sirve solo
    para "¿viste esa partida?".
  - No existe endpoint de "partidas totales jugadas" en ningún servicio:
      CHAMPION-MASTERY-V4 -> puntos, nivel y lastPlayTime, NO partidas jugadas.
      LEAGUE-V4           -> wins/losses de la season actual, por cola.
      ACCOUNT-V1/SUMMONER -> nada.
      League Client (LCU) -> solo local, no soportado para terceros.
  - [OK 2026-11-24] Paginación medida con una cuenta real: 100 por página y,
    cuando no quedan más, 200 con []. Esa cuenta tenía ~519 partidas
    recuperables (6 páginas). No prueba el tope de 1.000, pero confirma cómo se
    detecta el final: pedir páginas hasta que venga una vacía.
  - Un puuid sin partidas devuelve 404 "Data not found" [UNVERIFIED: observado
    por la comunidad, no documentado]. Manejo recomendado: tratá 404 y [] igual
    ("sin partidas").
  - Los detalles de partida se retienen 2 años; los timelines, 1 año.

Diseño recomendado: guardar las partidas en tu propia base desde el día 1
(append-only) y calcular los agregados por campeón vos mismo. Así, con el
tiempo, TU base acumula más historia que la ventana de 1000 de Riot. Ese es
el único camino real para acercarse a "toda la cuenta".

3. REGISTRO, TIPOS DE KEY Y REQUISITOS
================================================================================
Portal: https://developer.riotgames.com
Docs:   https://developer.riotgames.com/docs/portal

3.1 Development key (para desarrollar hoy mismo)
  - Se emite automáticamente al iniciar sesión con una cuenta de Riot.
  - SE DESACTIVA CADA 24 HORAS. Hay que regenerarla a mano (botón "Regenerate")
    o vas a ver 403 "Forbidden" de un día para el otro.
  - Solo para prototipos. Prohibido usarla en un producto público.
  - Rate limit real [OK verificado 2026-11-24 con una dev key]:
    X-App-Rate-Limit: 100:120,20:1  ->  100 req/2min y 20 req/1s por región.
    El portal no publica el número, pero los headers lo confirman. Los Términos
    viejos (2013) dicen 10 requests cada 10s (más estricto): no aplica en la
    práctica, pero no conviene abusar con una dev key.

3.2 Personal key (registrada, todavía NO pública)
  - Se pide en https://developer.riotgames.com/app-type con descripción del
    producto.
  - Límites: 20 req/1s + 100 req/2min por región. Sin verificación de sitio no
    hay aumentos.
  - Texto oficial: "You may not run your application for public consumption
    using a personal key… public consumption includes open alpha/beta tests."
  - Sirve para: uso propio, demo privada, desarrollo con datos reales.

3.3 Production key (lo que necesita una página pública)
  - Mismo formulario, marcando "larger scale", y Riot audita la app.
  - Límites iniciales: 500 req/10s + 30.000 req/10min POR REGIÓN (50 rps
    sostenidos). Para un sitio chico con caché es holgado.
  - Requisitos oficiales:
      * Sitio/dominio EN VIVO y funcional ("near-complete state").
      * Verificación de dominio: Riot te da un string que tenés que publicar en
        tu URL (https://developer.riotgames.com/how-to-verify-site.html).
      * Terms of Service y Privacy Policy visibles en el sitio.
      * Evidencia del flujo: screenshots, video demo o app testeable por Riot.
      * Un producto por key. Crear varias apps para saltar límites = violación.
  - Tiempos: revisión semanal de lo de la semana anterior; puede tardar hasta
    3 semanas (docs/faqs). Aprobado el caso de uso "player stats / match history".
  - Plan: construir con dev/personal y pedir la production key EN CUANTO el
    sitio esté deployado con dominio propio + páginas legales.

4. RATE LIMITS Y MANEJO DE 429
================================================================================
4.1 Números vigentes
  Personal  : 20 requests / 1 segundo  Y  100 requests / 2 minutos
  Producción: 500 requests / 10 segundos  Y  30.000 requests / 10 minutos
  Los límites se aplican POR REGIÓN: el cupo de na1 es independiente del de euw1.

  [OK] Observado en una dev key (2026-11-24):
    x-app-rate-limit     : 100:120,20:1     (100/2min y 20/1s)
    x-method-rate-limit  : 2000:60          (summoner-v4: 2.000 por minuto)
  [OK] Observado en la misma dev key (2026-11-25):
    x-method-rate-limit  : 1000:60          (match-v5)
    x-method-rate-limit  : 3000:10,180000:600  (spectator-v5, ver 7.9)
  El límite por método es MUCHO más alto que el de la app: el que te frena
  siempre va a ser el de la aplicación.

4.2 Tres capas de límite (todas por región)
  - application: por key, todas las methods juntas.
  - method     : por endpoint + key (ej. match-v5 detail).
  - service    : compartido entre TODAS las apps del mundo (el que te limita
                 sin avisar cuando Riot está bajo carga).
  Throughput efectivo = min(app, method, service).

4.3 Headers que devuelve Riot (leerlos, no adivinar)
  X-App-Rate-Limit        : "20:1,100:120"      -> permitido:segundos, por lista
  X-App-Rate-Limit-Count  : "18:1,95:120"      -> consumido en la ventana
  X-Method-Rate-Limit      / -Count            -> idem por endpoint
  Retry-After             : "5"                -> SOLO en 429, en segundos
  X-Rate-Limit-Type       : application|method|service  -> SOLO en 429

  [GOTCHA] Si un 429 NO trae X-Rate-Limit-Type, el que te frenó es el servicio
  de abajo (no el borde de la API): hay que retroceder mucho más fuerte.
  Las ventanas arrancan con tu primer request, no están alineadas al reloj.

4.4 Reglas de implementación (obligatorias)
  - Un token bucket por (región, method) en UN solo proceso. Si cada request
    de una Vercel Function crea su propio bucket, no hay control: por eso el
    ingest va en un worker/cron, no en el request del usuario.
  - Al 429: dormir Retry-After + jitter, drenar ese bucket, reintentar.
    Reintentos con exponential backoff + full jitter, máximo 3.
  - Nunca fan-out por page view: ver sección 10.
  - NUNCA rotar varias dev keys para multiplicar cupo. Ver 13.3.

================================================================================
5. ROUTING: HOST DE PLATAFORMA VS HOST REGIONAL
================================================================================
[GOTCHA] Este es el error #1 de las integraciones nuevas: pegarle a la región
equivocada devuelve 403/404 y parece "key inválida".

  - HOST DE PLATAFORMA  -> datos de un servidor (summoner, league, mastery)
                           {platform}.api.riotgames.com
  - HOST REGIONAL       -> datos cross-región (account, match)
                           {americas|asia|europe|sea}.api.riotgames.com

Plataformas (platformId):
  la1 (LA Norte)  la2 (LA Sur)  na1  br1  euw1  eun1  kr  jp1
  oc1  tr1  ru  ph2  sg2  th2  vn2  me1

Clusters regionales (para ACCOUNT-V1 y MATCH-V5):
  americas : na1, br1, la1, la2
  asia     : kr, jp1
  europe   : euw1, eun1, tr1, ru, me1
  sea      : oc1, ph2, sg2, th2, vn2

  El matchId viene con prefijo de plataforma: KR_7412345678, LA1_..., NA1_...
  El prefijo NO es el host: para el detalle usás el cluster regional.
  (Ej.: match KR_... -> https://asia.api.riotgames.com/lol/match/v5/matches/KR_...)

  Header:  X-Riot-Token: RGAPI-xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx

  - Deprecaciones: Riot mantiene versión vieja y nueva ~60 días y avisa por el
    blog/Discord de DevRel.
  - PUUID: string de exactamente 78 caracteres. Es el identificador estable;
    el nombre puede cambiar. Guardá SIEMPRE el puuid, nunca el nombre como PK.

7.1 ACCOUNT-V1 — Riot ID -> PUUID          (host REGIONAL)
--------------------------------------------------------------------------------
GET https://{cluster}.api.riotgames.com/riot/account/v1/accounts/by-riot-id/{gameName}/{tagLine}

  gameName : 3-16 caracteres, NO único (muchos "Faker"). Puede tener espacios
             y acentos ("Hide on bush"); el formato exacto no está documentado.
  tagLine  : 3-5 caracteres alfanuméricos (KR1, LAN, 1234...).
  Un Riot ID se identifica por la COMBINACIÓN gameName#tagLine.
  URL-encodeá ambos segmentos (espacios, acentos, ñ). El '#' NO va en la URL:
  va como separador → partís "Nombre#TAG" en dos path params.

  GET https://americas.api.riotgames.com/riot/account/v1/accounts/by-riot-id/Hide%20on%20bush/KR1
  200 -> {
    "puuid": "b2N0...78 chars...",
    "gameName": "Hide on bush",
    "tagLine": "KR1"
  }

  Variantes:
  GET /riot/account/v1/accounts/by-puuid/{puuid}                  -> mismo objeto

  [GOTCHA 2026-11-24] active-shards/by-game NO acepta "lol":
    GET /riot/account/v1/active-shards/by-game/lol/by-puuid/{puuid}
    400 {"status":{"message":"Bad Request - invalid parameter value lol,
         must be one of [val,lor,2xko]"}}
  O sea: sirve para Valorant, LoR y 2XKO, no para League.
  ¿Cómo saber la plataforma de un jugador entonces? Pedí 1 match id y mirá el
  prefijo (LA2_..., KR_..., EUW1_...); ese prefijo ES el platformId:
    GET https://americas.api.riotgames.com/lol/match/v5/matches/by-puuid/{puuid}/ids?count=1
    -> ["LA2_1639441889"]  => plataforma la2

  Notas:
  - Se puede consultar cualquier cuenta desde cualquier cluster: la data de
    cuentas es idéntica en americas/asia/europe/sea. Igual elegí el cluster
    correcto por consistencia y para no mezclar con match.
  - Desde el 2023-11-20 el Riot ID es la identidad oficial.
    summoner-v4/by-name/{summonerName} está DEPRECADO y Riot avisó que va a
    eliminar los summoner names de la API.

7.2.1 Lista de match IDs
GET https://{cluster}.api.riotgames.com/lol/match/v5/matches/by-puuid/{puuid}/ids

    ingest/worker. Se pide en el render del perfil con **revalidate 30** y con el
    tag `spectator`; `POST /api/sync` invalida ese tag (`expire: 0`) para que
    el "Actualizar" del perfil no siga mostrando una partida que ya terminó.

    el chip lo sigue contando en el browser con un `setInterval` de 1 s
    (`liveClockSeconds` en `src/lib/live.ts`).
    El conteo arranca con el valor del server y, si el absoluto
    (`ahora - gameStartTime`) se aleja más de 10 min de ese valor, cae a
    "base + tiempo desde el montaje": así un navegador con la hora mal no rompe
    el reloj, y un HTML servido 90 s tarde desde la caché igual se corrige.
  - El **estado** sí se revalida: una página abierta no se re-renderiza sola, así
    que el chip consulta `GET /api/en-vivo?platform=&puuid=` cada 45 s (y no
    cuando la pestaña está oculta). Ese endpoint vuelve a usar esta misma caché
    de 30 s, por lo que N espectadores de la misma partida comparten el request
    a Riot; el costo es como máximo ~2 requests por jugador por minuto mientras
    el badge está visible. Si Riot devuelve 404, el chip desaparece.
  - Un perfil caliente = 1 request por jugador por ventana de 30 s. Con dev key
    (100/2min) alcanza para ~50 jugadores distintos simultáneos.
  - El perfil puede tener varios puuids (Riot los reasigna): se consultan hasta
    2 y se corta en el primero que devuelve 200.
  - 404 -> null y cualquier otro error también: si Riot limita o la key venció,
    el perfil se dibuja sin badge. Nunca se rompe la página por este dato.

  Lo que este endpoint NO da:
  - No es la Spectator Grid: no hay kills, oro ni puntaje en vivo. Eso necesita
    la `encryptionKey` y un cliente spectator (fuera de alcance).
  - El `gameId` es el sufijo numérico del matchId futuro
    (`LA2_1639879656`), pero hasta que la partida termina y Riot la procesa,
    match-v5 no la devuelve [UNVERIFIED: no medido].

9.1 Cliente con token bucket (solo en el servidor / worker)
--------------------------------------------------------------------------------
type Bucket = { tokens: number; last: number };

const buckets = new Map<string, Bucket>();

const WINDOWS: Array<[number, number]> = [ [1, 20], [120, 100] ]; // [seg, tokens]

export async function riotFetch<T>(url: string, region: string): Promise<T> {
  const key = process.env.RIOT_API_KEY;
  if (!key) throw new Error("RIOT_API_KEY no configurada");

  for (let attempt = 0; attempt < 3; attempt++) {
    // espera hasta que el bucket de esta región tenga lugar
    const b = buckets.get(region) ?? { tokens: 20, last: Date.now() };
    const now = Date.now();
    const elapsed = (now - b.last) / 1000;
    b.tokens = Math.min(20, b.tokens + elapsed * (20 / 1));
    b.last = now;

    if (b.tokens < 1) {
      const deficit = 1 - b.tokens;
      await sleep((deficit * 1000) / 20);
      continue;
    }
    b.tokens -= 1;
    buckets.set(region, b);

    const res = await fetch(url, {
      headers: { "X-Riot-Token": key },
      cache: "no-store",
    });

    if (res.ok) return (await res.json()) as T;

    if (res.status === 429) {
      const retry = Number(res.headers.get("retry-after") ?? "1");
      await sleep((retry + Math.random()) * 1000);
      continue;
    }
    if (res.status >= 500) {
      await sleep(2 ** attempt * 1000 + Math.random() * 500);
      continue;
    }
    throw new RiotError(res.status, await res.text());
  }
  throw new Error("rate limit / reintentos agotados: " + url);
}

// Producción: respetar 20/s y 100/2min. Además, un semáforo serializado
// (por proceso) evita que dos jobs del worker se pisen.

9.2 Resolver Riot ID -> puuid (cachear para siempre)

function clusterFor(platform: string) {
  if (["na1","br1","la1","la2"].includes(platform)) return "americas";
  if (["kr","jp1"].includes(platform)) return "asia";
  if (["euw1","eun1","tr1","ru","me1"].includes(platform)) return "europe";
  return "sea"; // oc1, ph2, sg2, th2, vn2
}

async function resolveRiotId(gameName: string, tagLine: string, platform: string) {
  const c = clusterFor(platform);
  const url = `https://${c}.api.riotgames.com/riot/account/v1/accounts/by-riot-id/` +
              `${encodeURIComponent(gameName)}/${encodeURIComponent(tagLine)}`;
  return riotFetch<{ puuid: string; gameName: string; tagLine: string }>(url, c);
}

9.4 Agregado por campeón (el corazón del producto)
--------------------------------------------------------------------------------
type ChampAgg = { championId: number; championName: string; games: number; wins: number };

function aggregateByChampion(matches: MatchDto[], puuid: string): ChampAgg[] {
  const map = new Map<string, ChampAgg>();
  for (const m of matches) {
    const p = m.info.participants.find((x) => x.puuid === puuid);
    if (!p) continue;
    // excluir customs: riesgo legal (ver 13) y ruido de stats
    if (m.info.queueId === 0) continue;

    // Clave de agrupación: championName SIEMPRE.
    // Riot recomienda championName y avisa que championId es inválido en
    // partidas < 11.4. Además championName == DDragon.data[*].id.
    const k = p.championName;

    const cur = map.get(k) ?? {
      championId: p.championId, championName: p.championName, games: 0, wins: 0,
    };
    cur.games += 1;
    if (p.win) cur.wins += 1;
    map.set(k, cur);
  }
  return [...map.values()]
    .map((a) => ({ ...a, winrate: a.wins / a.games }))
    .sort((a, b) => b.games - a.games);
}

// "Campeón más jugado" = aggregateByChampion(...)[0]
// "Filtrar por campeón" = el mismo array, buscado por championName.

9.5 Backfill paginado (worker, nunca en un request de usuario)

async function backfill(puuid: string, cluster: string, maxPages = 10) {
  // 10 páginas x 100 = 1.000 = el tope real de Riot
  for (let page = 0; page < maxPages; page++) {
    const ids = await riotFetch<string[]>(
      `https://${cluster}.api.riotgames.com/lol/match/v5/matches/by-puuid/${puuid}/ids` +
      `?start=${page * 100}&count=100`, cluster);
    if (ids.length === 0) break;               // fin del historial disponible
    for (const id of ids) {
      if (await existsInDb(id)) continue;      // idempotente
      const m = await riotFetch<MatchDto>(
        `https://${cluster}.api.riotgames.com/lol/match/v5/matches/${id}`, cluster);
      await saveMatch(m);                      // guarda + upsert de agregados
    }
    await updateSyncCursor(puuid, page);
  }
}

10. ARQUITECTURA DE CACHÉ RECOMENDADA
================================================================================
Regla de oro: NINGÚN page view le pega a Riot. El web tier lee SOLO de tu caché
/ base. El ingest corre en un worker.

Tres capas:

  (1) CDN / render cache  — la página
      - HTML cacheado 30-300s por URL (perfil/puuid), swr.
      - Partidas individuales son inmutables: cache "max".

  (2) Caché de Riot — Redis / KV  (lo que evita quemar el rate limit)
      riotId  -> puuid                    TTL: permanente
      matchId -> match JSON completo      TTL: permanente (inmutable)
      puuid   -> agregado por campeón     TTL: 10-30 min
      lock    -> SET NX PX por puuid      colapsa N visitas concurrentes en 1 sync

  (3) Base de datos — Postgres (Neon/Supabase free)  (historia propia)
      matches(match_id TEXT PRIMARY KEY, platform_id TEXT, cluster TEXT,
              queue_id INT, game_version TEXT, game_start_ts BIGINT,
              game_duration_s INT, payload JSONB, fetched_at TIMESTAMPTZ)
      puuid_matches(puuid TEXT, match_id TEXT, PRIMARY KEY (puuid, match_id))
      champion_stats(puuid TEXT, champion_id INT, champion_name TEXT,
                     games INT, wins INT, PRIMARY KEY (puuid, champion_id))
      puuid_sync(puuid TEXT PRIMARY KEY, cluster TEXT, last_synced_at TIMESTAMPTZ,
                 oldest_match_ts BIGINT,
                 backfill_state TEXT CHECK (backfill_state IN
                   ('none','running','done','partial')),
                 ids_cursor INT DEFAULT 0)

TTLs sugeridos:
  match detail        : ∞ (inmutable)
  puuid_matches       : ∞
  agregado por campeón: 30 min (soft)
  ids página 0        : 5-15 min
  account -> puuid    : ∞

Refresh incremental (lo ÚNICO que puede tocar un page view, y solo si no hay caché):
  si puuid_sync.last_synced_at > now() - 30min -> devolver agregado cacheado (0 calls)
  si no -> pedir ids de la página 0 (count=20) -> diff con puuid_matches
           -> bajar solo los nuevos (k calls, secuencial) -> upsert -> devolver

Por qué el worker y no la función serverless:
  El token bucket tiene que vivir en un proceso que persiste y que atiende todo
  el tráfico de Riot. En serverless cada invocación es un proceso nuevo: no hay
  bucket compartido y te comés 429. Opciones de worker gratis:
    - GitHub Actions schedule: mínimo 5 min, se auto-desactiva a los 60 días sin
      actividad en repos públicos (chequear y reactivar).
    - Un proceso Node en Fly.io / Railway (o VPS chico).
    - Vercel Cron en Hobby: mínimo 1 vez por día (demasiado grueso para esto).

Aplicar la production key: el sitio público la necesita. Sin ella, el proyecto
solo puede ser privado/demo.

11. COSTO EN REQUESTS
================================================================================
  | Escenario                                | Cold (calls)         |
  |------------------------------------------|----------------------|
  | Riot ID -> puuid                         | 1                    |
  | Perfil "últimas 20" (ids + 20 detalles)  | 1 + 1 + 20 = 22      |
  | Refresh incremental con 3 partidas nuevas| 1 + 3 = 4            |
  | Backfill completo (10 páginas + 1000)    | 1 + 10 + 1000 = 1011 |
  | Segundo usuario abre el mismo perfil     | 1 + 0 (ya cacheadas) |
  | Chip "en partida ahora" (spectator)      | 1 (2 si hay dos puuids) |
  | ¿Hay partidas nuevas? (ids count=1)      | 1                    |
  | Una vuelta de "Actualizar ahora"         | 30 (RIOT_SYNC_CHUNK) |

  El botón "Actualizar ahora" del perfil llama a /api/sync en bucle: cada
  vuelta gasta hasta RIOT_SYNC_CHUNK (30) requests y baja ~27 detalles (el resto
  se va en IDs y en reintentos). Con dev key son ~15 s por vuelta y ~27
  partidas: 500 pendientes = ~19 vueltas (~5 min) con la luna girando.

  La verificación de "¿hay partidas nuevas?" (ADR-018) usa el mismo
  `startTime` de 2 años que el ingest, redondeado al día para que la URL no
  cambie en cada vista y el cache de 45 s acierte. La última vuelta de
  /api/sync agrega 1 request para confirmar `upToDate` (si no queda
  presupuesto, devuelve `null` y el cliente no afirma "Actualizado").

  El chip de spectator es el único que no se puede cachear largo: con
  revalidate 60, un jugador activo cuesta 1 call/min mientras alguien mire su
  perfil. 100/2min de la dev key -> ~50 jugadores distintos a la vez.

  Throughput:
  - dev/personal: 20/1s + 100/2min = 0,83 rps sostenidos.
      22 calls ≈ 26s  |  backfill 1011 ≈ 20 min  -> inviable por usuario.
  - producción   : 50 rps sostenidos.
      22 calls ≈ 0,5s |  backfill 1011 ≈ 20s.
  Conclusión: con caché, un sitio chico vive cómodo con producción; dev sirve
  solo para desarrollar (y el backfill se corre en background, nunca en el
  request del usuario).

12. CÓDIGOS DE ERROR Y TROUBLESHOOTING
================================================================================
  400  sintaxis/parámetro inválido (count>100, startTime>endTime, tipo mal)
  401  falta la key o está vacía
       -> {"status":{"message":"Cannot process request apikey or authorization
           header is empty","status_code":401}}          [OK] verificado
  403  key inválida / expirada (dev key >24h) / blacklisted
       TAMBIÉN: host equivocado (plataforma vs regional) o path inexistente
       -> si el resto anda y una ruta da 403, sospechá del host/path primero
  404  recurso no encontrado (puuid sin partidas, matchId inexistente)
       En spectator-v5 es el caso NORMAL: "no está en partida" (7.9).
  415  Content-Type incorrecto (solo en POST)
  429  rate limit -> leer Retry-After + X-Rate-Limit-Type
  500  error interno de Riot -> backoff y reintentar
  503  servicio no disponible -> backoff; revisar lol-status-v4
  405/502/504  aparecen listados en algunas páginas de servicio

  El cuerpo de un error NO está garantizado como JSON: ramificá por status.
  Checklist de "no me anda":
    1. ¿La key tiene menos de 24h (dev)? -> regenerar.
    2. ¿Host correcto? account/match = regional; summoner/league/mastery = plataforma.
    3. ¿count <= 100?  4. ¿URL-encodeaste gameName?  5. ¿'#' fuera de la URL?
    6. ¿El cluster corresponde a la plataforma? (7.1 y sección 5)

13.1 Registro y auditoría
  Todo producto debe estar registrado y auditado en el Developer Portal. Cambios
  o features nuevas también se auditan. Un sitio público con key personal/dev es
  una violación de política, no una simple molestia de rate limit.

13.2 Atribución obligatoria (texto visible en el sitio)
  Incluir el boilerplate: "<Tu producto> isn't endorsed by Riot Games and doesn't
  reflect the views or opinions of Riot Games or anyone officially involved in
  producing or managing Riot Games properties. Riot Games, and all associated
  properties are trademarks or registered trademarks of Riot Games, Inc."
  (Traducirlo es riesgoso: dejalo en inglés y agregá una nota en español.)

13.3 Prohibiciones que nos tocan
  - No exponer tu propia API a terceros ("no apps serving as a data broker
    between our API and another third-party company"). Nada de /api/public/*
    que devuelva datos crudos de Riot.
  - No crear múltiples apps para saltar rate limits. No compartir/vender la key.
  - No revender ni licenciar Game Information sin aprobación escrita de Riot.
    Publicidad común sí está permitida; cobrar por el acceso a los datos, no.
  - Assets: solo Data Dragon, Press Kit y packs oficiales. No usar arte propio
    de terceros.
  - No mostrar historial de partidas de cola CUSTOM sin opt-in del jugador.
  - No mostrar winrates de Augments ni de ítems de Arena.
  - No hacer apps que imiten productos de Riot (cuidado con el branding).
  - Si monetizás: el estado del producto debe ser "Approved or Acknowledged" y
    tiene que existir un tier gratuito. Nada de apuestas.

13.4 Privacidad / GDPR
  Los datos de invocador son datos personales. Riot puede reenviarte pedidos de
  borrado de usuarios finales. Necesitás:
    - Privacy Policy publicada (además es requisito para la production key).
    - Un mecanismo para borrar los datos de un puuid a pedido.
    - No loguear puuids/nombres innecesariamente.

13.5 Caché (recomendación oficial, no obligación)
  [SECONDARY] Los TTL que circulan como "oficiales" (historial ~30 min, iconos y
  nombres ~24 h, estáticos más) vienen de un espejo comunitario del texto que
  Riot publicaba. Son razonables y los usamos, pero no son un requisito
  contractual: lo que sí es obligatorio es no abusar del rate limit.

13.6 Nombre del sitio
  No uses "Riot", "League of Legends" ni logos como si fueras oficial. Un
  "<algo> para LoL" con disclaimer alcanza. Evitá dominios tipo
  riot-stats.com / leagueoflegends-tracker.com.
