# Vercel Functions Limits
Copy pageCopy page
The table below outlines the limits and restrictions of using Vercel Functions with Fluid compute:  
| Feature  | Limits  |  
| --- | --- |  
| [Maximum memory](https://vercel.com/docs/functions/limitations#memory-size-limits)  | Hobby: 2 GB, Pro and Ent: 4 GB  |  
| [Maximum duration](https://vercel.com/docs/functions/limitations#max-duration)  | Hobby: 300s default and maximum. Pro and Enterprise: 300s default, 800s maximum, and 1800s extended maximum Beta. See [max duration](https://vercel.com/docs/functions/limitations#max-duration) for requirements and configuration.  |  
|  [Size](https://vercel.com/docs/functions/limitations#bundle-size-limits) (uncompressed)  | 250 MB, or 500 MB for [Python](https://vercel.com/docs/functions/runtimes/python). [Large functions](https://vercel.com/docs/functions/limitations#large-functions-beta) support up to 5 GB Beta.  |  
| Concurrency  | Scales automatically based on demand  |  
| [Cost](https://vercel.com/docs/functions/runtimes)  | Pay for active CPU time and provisioned memory time  |  
| [Regions](https://vercel.com/docs/functions/runtimes#location)  | Runs in a single region by default (`iad1`), which you can [change](https://vercel.com/docs/functions/configuring-functions/region#setting-your-default-region).  
Pro and Enterprise teams can set [multiple regions](https://vercel.com/docs/functions/configuring-functions/region#limits)  |  
| [API Coverage](https://vercel.com/docs/functions/limitations#api-support)  | Full Node.js coverage  |  
| [File descriptors](https://vercel.com/docs/functions/limitations#file-descriptors)  | 1,024 shared across concurrent executions (including runtime usage)  |  
##  [Functions name](https://vercel.com/docs/functions/limitations#functions-name)[](https://vercel.com/docs/functions/limitations#functions-name)
The following limits apply to the function's name when using [Node.js runtime](https://vercel.com/docs/functions/runtimes/node-js):
  * Maximum length of 128 characters. This includes the extension of the file (e.g. `apps/admin/api/my-function.js` is 29 characters)
  * No spaces are allowed. Replace them with a `-` or `_` (e.g. `api/my function.js` isn't allowed)


##  [Bundle size limits](https://vercel.com/docs/functions/limitations#bundle-size-limits)[](https://vercel.com/docs/functions/limitations#bundle-size-limits)
Vercel places restrictions on the maximum size of the deployment bundle for functions to ensure that they execute in a timely manner.
For Vercel Functions, the maximum uncompressed size is 250 MB including layers which are automatically used depending on [runtimes](https://vercel.com/docs/functions/runtimes). These limits are [enforced by AWS](https://docs.aws.amazon.com/lambda/latest/dg/gettingstarted-limits.html). For [Python functions](https://vercel.com/docs/functions/runtimes/python), the maximum uncompressed size is 500 MB.
You can use [`includeFiles` and `excludeFiles`](https://vercel.com/docs/project-configuration/vercel-json#functions) to specify items which may affect the function size. These configurations are not supported in Next.js, instead use [`outputFileTracingIncludes`](https://nextjs.org/docs/app/api-reference/config/next-config-js/output).
###  [Troubleshooting the 250 MB limit](https://vercel.com/docs/functions/limitations#troubleshooting-the-250-mb-limit)[](https://vercel.com/docs/functions/limitations#troubleshooting-the-250-mb-limit)
When a function exceeds the limit, the build fails with this error:

```
The Vercel Function "api/hello" is 300mb uncompressed which exceeds the maximum uncompressed size limit of 250mb.
```

If your project is eligible for [large functions](https://vercel.com/docs/functions/limitations#large-functions-beta), the function can deploy without other changes once large functions are enabled. To find out what's making a function large, add the `VERCEL_ANALYZE_BUILD_OUTPUT` [environment variable](https://vercel.com/docs/environment-variables) with the value `1` and redeploy. The build logs then list each function's uncompressed size and its largest files:

```
Function : /api
Size     : 1991.54 MB
  Large dependencies:
    • _vendor/tensorflow/libtensorflow_cc.so.2: 972.15 MB
    • _vendor/tensorflow/include: 307.87 MB
```

Common causes of large functions include:
  * Heavy dependencies: Packages that ship binaries, such as [Puppeteer with its bundled Chromium](https://vercel.com/docs/functions/limitations#running-puppeteer-and-headless-chromium), or machine learning libraries. Duplicate copies of the same package also add size. Run `npm ls <package>` to see why a package is installed, and `npm dedupe` to remove duplicates.
  * Static assets traced into the function: Images, videos, or large JSON files that server code imports or reads are packaged with the function. Serve them from the `public` directory or external storage instead.
  * Dynamic imports with variable paths: An import or `require` with a path built at runtime can make the bundler include every file in a directory. Use static import paths where you can.


To exclude files a function doesn't need, use `excludeFiles` in `vercel.json`. This example keeps the `public` and `test` directories out of every function under `api`:
vercel.json

```
{
  "$schema": "https://openapi.vercel.sh/vercel.json",
  "functions": {
    "api/**": {
      "excludeFiles": "{public,test}/**"
    }
  }
}
```

In Next.js, use [`outputFileTracingExcludes`](https://nextjs.org/docs/app/api-reference/config/next-config-js/output) in `next.config.js` instead.
###  [Running Puppeteer and headless Chromium](https://vercel.com/docs/functions/limitations#running-puppeteer-and-headless-chromium)[](https://vercel.com/docs/functions/limitations#running-puppeteer-and-headless-chromium)
The `puppeteer` package downloads a Chrome build of about 280 MB for Linux when you install it, which is larger than the standard bundle size limit. To take screenshots, generate PDFs, or automate a browser in a function, install [`puppeteer-core`](https://pptr.dev/guides/installation), which doesn't download a browser, and pair it with [`@sparticuz/chromium`](https://github.com/Sparticuz/chromium), a Chromium build for serverless environments.
`@sparticuz/chromium` ships a compressed Chromium binary inside the package, so the binary counts toward the function's bundle size. If the function exceeds the 250 MB limit, enable [large functions](https://vercel.com/docs/functions/limitations#large-functions-beta).
app/api/title/route.ts

```
import chromium from '@sparticuz/chromium';
import puppeteer from 'puppeteer-core';
 
export async function GET() {
  const browser = await puppeteer.launch({
    args: await puppeteer.defaultArgs({
      args: chromium.args,
      headless: 'shell',
    }),
    executablePath: await chromium.executablePath(),
    headless: 'shell',
  });
 
  try {
    const page = await browser.newPage();
    await page.goto('https://example.com', { waitUntil: 'networkidle2' });
    return Response.json({ title: await page.title() });
  } finally {
    await browser.close();
  }
}
```

Next.js keeps `puppeteer-core` and `@sparticuz/chromium` out of the server bundle by default. If your Next.js version bundles them, add both packages to [`serverExternalPackages`](https://nextjs.org/docs/app/api-reference/config/next-config-js/serverExternalPackages) in `next.config.js`.
If you can't use large functions, install `@sparticuz/chromium-min` instead. It leaves the binary out of the package, and you pass `chromium.executablePath()` the URL of a Chromium archive that you host. The function downloads the archive when it starts, which makes the first request to a new function instance slower. The [Puppeteer on Vercel template](https://vercel.com/templates/next.js/puppeteer-on-vercel) shows this setup.
Chromium uses more memory than most functions need. The `@sparticuz/chromium` documentation recommends 1,600 MB or more. If the function runs out of memory or times out, raise its [memory](https://vercel.com/docs/functions/configuring-functions/memory) or [maximum duration](https://vercel.com/docs/functions/configuring-functions/duration).
##  [Large functions Beta](https://vercel.com/docs/functions/limitations#large-functions-beta)[](https://vercel.com/docs/functions/limitations#large-functions-beta)
Large functions let you deploy uncompressed bundles up to 5 GB. Use them for workloads that ship large dependencies, model files, or binaries. Large functions are supported on Node.js, Bun, and Python runtimes.
Large functions require [fluid compute](https://vercel.com/docs/fluid-compute) with [Active CPU](https://vercel.com/docs/functions/usage-and-pricing#active-cpu) enabled. Fluid compute is enabled by default for new projects.
###  [Enable large functions](https://vercel.com/docs/functions/limitations#enable-large-functions)[](https://vercel.com/docs/functions/limitations#enable-large-functions)
New projects are eligible for large functions by default. For existing projects, opt in by setting the `VERCEL_SUPPORT_LARGE_FUNCTIONS` [environment variable](https://vercel.com/docs/environment-variables).
The environment variable always takes precedence over the project default. Set it to `1` to enable support for large functions, or `0` to disable, for both new and existing projects.
You can set `VERCEL_SUPPORT_LARGE_FUNCTIONS` as a project [environment variable](https://vercel.com/docs/environment-variables) in your project settings or with the [Vercel CLI](https://vercel.com/docs/cli/env).
In eligible projects, Vercel only uses the large functions beta for Functions that exceed the standard bundle size limit. Functions that fit within the standard limit continue to use the standard path.
###  [Supported runtimes](https://vercel.com/docs/functions/limitations#supported-runtimes)[](https://vercel.com/docs/functions/limitations#supported-runtimes)
Large functions are supported on the following runtimes:
  * [`nodejs`](https://vercel.com/docs/functions/runtimes/node-js)
  * [`bun`](https://vercel.com/docs/functions/runtimes/bun)
  * [`python`](https://vercel.com/docs/functions/runtimes/python)


Large functions are supported for projects using [Secure Compute](https://vercel.com/docs/networking/secure-compute) or [Static IPs](https://vercel.com/docs/networking/static-ips). They are not yet supported with [BYOC](https://vercel.com/docs/networking/bring-your-own-cloud).
##  [Max duration](https://vercel.com/docs/functions/limitations#max-duration)[](https://vercel.com/docs/functions/limitations#max-duration)
This refers to the longest time a function invocation can run before Vercel terminates it. For request handlers, this includes time spent processing the request and sending the response, including streamed responses.
While Vercel Functions have a default duration, this duration can be extended using the [maxDuration config](https://vercel.com/docs/functions/configuring-functions/duration). If a Vercel Function doesn't complete within the duration, a 504 error code ([`FUNCTION_INVOCATION_TIMEOUT`](https://vercel.com/docs/errors/function_invocation_timeout)) is returned.
With [fluid compute](https://vercel.com/docs/fluid-compute) enabled, Vercel Functions have the following defaults and maximum limits:
###  [Node.js, Bun, and Python runtimes](https://vercel.com/docs/functions/limitations#node.js-bun-and-python-runtimes)[](https://vercel.com/docs/functions/limitations#node.js-bun-and-python-runtimes)  
|   | Default  | Maximum  | Extended maximum  |  
| --- | --- | --- | --- |  
| Hobby  | 300s (5 minutes)  | 300s (5 minutes)  | -  |  
| Pro  | 300s (5 minutes)  | 800s  | 1800s (30 minutes) Beta  |  
| Enterprise  | 300s (5 minutes)  | 800s  | 1800s (30 minutes) Beta  |  
The 800 second maximum is generally available for Pro and Enterprise teams. The 1800 second extended maximum is in beta. Values above 800 seconds require function-level configuration and are only supported for specific Node.js, Bun, and Python runtime versions. Durations above 800 seconds are supported with [Secure Compute](https://vercel.com/docs/networking/secure-compute) and [Static IPs](https://vercel.com/docs/networking/static-ips), but not with [BYOC](https://vercel.com/docs/networking/bring-your-own-cloud). See [configuring maximum duration](https://vercel.com/docs/functions/configuring-functions/duration#extended-max-duration-beta) for the supported runtimes and examples.
For workloads that require unlimited execution time, use [Vercel Workflows](https://vercel.com/docs/workflows), which allow your code to pause, resume, and maintain state for minutes to months without duration limits.
###  [Edge runtime](https://vercel.com/docs/functions/limitations#edge-runtime)[](https://vercel.com/docs/functions/limitations#edge-runtime)
Vercel Functions using the [Edge runtime](https://vercel.com/docs/functions/runtimes/edge) must begin sending a response within 25 seconds to maintain streaming capabilities beyond this period, and can continue [streaming](https://vercel.com/docs/functions/streaming-functions) data for up to 300 seconds.
##  [Memory size limits](https://vercel.com/docs/functions/limitations#memory-size-limits)[](https://vercel.com/docs/functions/limitations#memory-size-limits)
Vercel Functions have the following defaults and maximum limits:  
|   | Default  | Maximum  |  
| --- | --- | --- |  
| Hobby  | 2 GB / 1 vCPU  | 2 GB / 1 vCPU  |  
| Pro / Enterprise  | 2 GB / 1 vCPU  | 4 GB / 2 vCPU  |  
Users on Pro and Enterprise plans can [configure the default memory size](https://vercel.com/docs/functions/configuring-functions/memory#setting-your-default-function-memory-/-cpu-size) for all functions in the dashboard.
The maximum size for a Function includes your JavaScript code, imported libraries and files (such as fonts), and all files bundled in the function.
If you reach the limit, make sure the code you are importing in your function is used and is not too heavy. You can use a package size checker tool like [bundle](https://bundle.js.org/) to check the size of a package and search for a smaller alternative.
##  [Request body size](https://vercel.com/docs/functions/limitations#request-body-size)[](https://vercel.com/docs/functions/limitations#request-body-size)
Vercel Functions accept request bodies up to 4.5 MB by default (see [How do I bypass the 4.5MB body size limit of Vercel Functions](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions)). Request bodies up to 20 MiB are available in Public Beta for the Node.js, Python, and Bun runtimes.
To enable the 20 MiB limit:
  1. Enable [fluid compute](https://vercel.com/docs/fluid-compute#enabling-fluid-compute) for your project.
  2. Set your project's [function memory](https://vercel.com/docs/functions/configuring-functions/memory#setting-your-default-function-memory-/-cpu-size) to Performance (4 GB), available on Pro and Enterprise plans.
  3. Set `VERCEL_SUPPORT_LARGE_REQUEST_BODY=1` in your project's [environment variables](https://vercel.com/docs/environment-variables) for the environments you want to enable, then redeploy.


The opt-in applies to the whole project in each selected environment, so you can test it in Preview before enabling it in Production.
When enabled, Routing Middleware receives headers and metadata but cannot access request bodies. Functions and Routing Middleware using the [Edge runtime](https://vercel.com/docs/functions/runtimes/edge) keep the 4.5 MB limit. Switch to the Node.js runtime to use larger bodies.
For larger requests, start reading the body as soon as it arrives. Where possible, process the data in smaller chunks to keep uploads moving and reduce memory use.
Requests exceeding the applicable limit return [413: `FUNCTION_PAYLOAD_TOO_LARGE`](https://vercel.com/docs/errors/function_payload_too_large).
The response body size limit is 4.5 MB, except for [streamed responses](https://vercel.com/docs/functions/streaming-functions).
##  [File descriptors](https://vercel.com/docs/functions/limitations#file-descriptors)[](https://vercel.com/docs/functions/limitations#file-descriptors)
File descriptors are unique identifiers that the operating system uses to track and manage open resources like files, network connections, and I/O streams. Think of them as handles or references that your application uses to interact with these resources. Each time your code opens a file, establishes a network connection, or creates a socket, the system assigns a file descriptor to track that resource.
Vercel Functions have a limit of 1,024 file descriptors shared across all concurrent executions. This limit includes file descriptors used by the runtime itself, so the actual number available to your application code will be strictly less than 1,024.
File descriptors are used for:
  * Open files
  * Network connections (TCP sockets, HTTP requests)
  * Database connections
  * File system operations


If your function exceeds this limit, you might encounter errors related to "too many open files" or similar resource exhaustion issues.
To manage file descriptors effectively, consider the following:
  * Close files, database connections, and HTTP connections when they're no longer needed
  * Use connection pooling for database connections
  * Implement proper resource cleanup in your function code

##  [Cost and usage](https://vercel.com/docs/functions/limitations#cost-and-usage)[](https://vercel.com/docs/functions/limitations#cost-and-usage)
The Hobby plan offers functions for free, within [limits](https://vercel.com/docs/limits). The Pro plan extends these limits, and charges usage based on active CPU time and provisioned memory time for Vercel Functions.
Active CPU time is based on the amount of CPU time your code actively consumes, measured in milliseconds. Waiting for I/O (e.g. calling AI models, database queries) does not count towards active CPU time. Provisioned memory time is based on the memory allocated to your function instances multiplied by the time they are running.
It is important to make sure you've set a reasonable [maximum duration](https://vercel.com/docs/functions/configuring-functions/duration) for your function. See "Managing usage and pricing for [Vercel Functions](https://vercel.com/docs/functions/usage-and-pricing)" for more information.
